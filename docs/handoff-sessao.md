## 1. O que é o portal e como funciona

**Produto:** portal da comunidade Bajeiros (Baja, sem vínculo SAE). Piloto = **validador visual 3D de gaiola** contra as regras B6 do RATBSB emenda 7 (~40 regras automáticas + itens manuais). Visão: SaaS p/ estudantes — contas, equipes de universidade c/ recursos compartilhados, N projetos (projeto = carro), features pagas (Stripe, Pix/usuário/mês simbólico), LGPD por design, dados modelados via contratos **ODCS** (`contracts/*.odcs.yaml`).

**Monorepo npm workspaces** (repo público `github.com/pedrotaem/bajeiros-portal`, sem LICENSE = todos direitos reservados):

- `packages/core` — `@bajeiros/core`: motor de regras B6 + modelos, TS puro, zero deps. Exporta fonte direto (`"./*": "./src/*.ts"`, sem build). Roda no browser E no backend.
- `apps/web` — SPA Vite+React+react-three-fiber+zustand. **Landing = página inicial** (`Landing.tsx`: todo acesso à raiz cai nela; CTA único "Editor / Validador de Gaiola"; botão de conta no topo direito; convite `#convite=` pula direto p/ login; "Sobre o portal" na topbar reabre) + editor 3D (nós/membros, wizard 6 passos, massa, juntas, manequim) + telas de sessão (login/perfil/projetos/**equipes**).
- `apps/api` — Hono TS. Local: `@hono/node-server` porta 8787; prod: `src/lambda.ts` (hono/aws-lambda). Módulos: `identity` (bootstrap idempotente `POST /api/v1/me`, perfil, consents append-only, export LGPD c/ equipes, soft delete), `projects` (CRUD + snapshots versionados c/ lock otimista `expectedSeq`→409, validação server-side c/ `evaluate()` do core, limites free 2 projetos/10 versões→403, transferência p/ equipe) e `teams` (equipes, convites, papéis — fase 14). **Policy layer** `src/policy.ts`: `can()`/`outranks()` decidem RBAC fino (owner>admin>member); a RLS só garante isolamento membro×não-membro. Erros RFC 9457 (`problem()` usa `c.body`, NÃO `c.json` — c.json sobrescreve content-type).
- `contracts/` — 7 contratos ODCS v3 (user, consent, team, project, cage-snapshot, subscription, audit-event) c/ `pii`/`legalBasis`/`retention` por propriedade. Validador: `npm run contracts:check`. **Regra: mudou schema → muda contrato no MESMO PR** (ADR-006).
- `infra/` — Terraform S3+CloudFront+ACM+Route53+OIDC (site estático v1; NADA aplicado ainda).
- `docs/` — planos v1/v2, revisões 3-personas, `adr/001–008`, `threat-model.md`, `runbook.md`.

**Banco/segurança:** Postgres c/ **RLS** (migrações `apps/api/migrations/0001_init.sql` + `0002_teams.sql`): app conecta como `bajeiros_app` (NOBYPASSRLS); `withUser()` em `db.ts` roda cada request em transação c/ `set_config('app.user_id', $1, true)`. Helpers SECURITY DEFINER: `user_team_ids()`/`team_has_members()` (evitam recursão de RLS) e, da 0002, `team_member_profiles()` (nomes/e-mails dos colegas — users tem RLS "só a própria linha") e `accept_team_invite()` (quem aceita ainda não é membro, a RLS o bloquearia; a fn valida hash+expiração+e-mail e consome o convite). `consents`/`cage_snapshots`/`audit_events` são append-only por GRANT. **Testes de isolamento (gate M1) e de autorização por papel (gate M2)** em `apps/api/src/test/rls.test.ts` e `teams.test.ts`. **Armadilha aprendida:** `INSERT … RETURNING` exige que a linha nova passe na policy de SELECT — criar equipe gera o uuid na app, insere sem RETURNING, insere a membership na MESMA transação e só então faz SELECT.

**Dev local (SEM Docker — máquina não tem):**

```bash
npm run db:start -w @bajeiros/api   # Postgres embutido porta 5433 (embedded-postgres 17.10.0-beta.17;
                                    # initdbFlags UTF8 obrigatórias — default Windows WIN1252 quebra c/ "≤")
npm run dev -w @bajeiros/api        # API 8787 (AUTH_MODE=dev)
npm run dev -w @bajeiros/web        # Vite (proxy /api→8787; 5173-75 podem estar ocupadas → vai p/ 5176)
```

Login dev: `POST /api/v1/dev/token {email,name}` → Bearer HS256 c/ claims iguais Cognito (sub uuid estável por e-mail via localStorage do front). Testes: Postgres embutido efêmero porta 5434 via globalSetup. **87 testes** (38 core + 14 web + 35 api). node-pg-migrate v9 = import nomeado `{ runner }`. Se os processos dev caírem junto c/ a sessão do Claude, subir **destacado** via `Start-Process` (PowerShell) — os background tasks do Claude Code morrem no fim da sessão.

## 2. O que foi feito e por quê (resumo cronológico)

1. **Fundação v1** (plano `docs/plano-producao.md`, revisado por 3 personas em `docs/revisao-plano.md`): repo higiene, ESLint/Prettier (2 regras react-hooks v6 rebaixadas a warn), CI hardened (SHA-pinned, gitleaks binário v8.30.1 — a action v3 é bugada "stderr is not empty"), `npm ci --ignore-scripts` (testado verde), deploy.yml OIDC staging→prod gated (no-op até variable `DEPLOY_ENABLED=true`), Terraform static-site.
2. **Plano v2 SaaS** (`docs/plano-producao-v2.md` + `docs/revisao-plano-v2.md`, 17 consensos aplicados): arquitetura serverless AWS. Decisões fechadas em ADRs: serverless API GW+Lambda (001), Aurora Serverless v2 scale-to-zero (002), Cognito Essentials→Plus no M3 (003), **Stripe** (004, decisão do Pedro; Pix recorrente = send_invoice ou Pix Automático, verificar), monorepo (005), escopo ODCS sem codegen (006), RDS Data API sem VPC (007), **região dados = sa-east-1** (008, voto de minerva da persona Segurança; verificar Data API/0 ACU em sa-east-1 no apply). Marcos: M1 contas+projetos → M2 equipes → M3 pagamentos.
3. **GitHub configurado:** secret scanning+push protection, CodeQL default setup, Dependabot (baseline tinha 7 vulns; PRs abertos), environments `staging`/`production` (reviewer pedrotaem), ruleset `main-protection` (PR + checks "Secret scan (gitleaks)" e "Lint · Typecheck · Test · Build" obrigatórios, sem force-push). **Claude NÃO consegue mergear PR (classifier bloqueia) — merge é do Pedro.**
4. **API implementada** (PR #9) e **telas de sessão** (PR #10, base = branch do #9, retarget auto p/ main). Smoke test real no Chrome ok (login→projeto→salvar v1).
5. **Estudo de design/UX** (artefato Claude "Estudo UX Bajeiros" c/ telas reais): diagnóstico "ausência de hierarquia e sequência". Proposta: onboarding (R1), modos Checar (problemas primeiro) vs Modelar (R2), camada de linguagem humana antes do código B6 (R3), persistência única (R4), topbar compacta (R5). Bugs achados: **Esc não fecha modais; labels 3D vazam por cima dos modais (z-index); logout silencioso no reload; câmera inicial não enquadra**.
6. **Equipes e convites — fase 14** (PR #11, base #10): migração `0002_teams.sql`, policy layer `can()`/`outranks()`, convite por **link copiável** (token 32B só na resposta de criação, sha256 no banco, 7 dias, vinculado ao e-mail, resposta uniforme sem enumeração — C9; cap 20 pendentes; revogação), papéis c/ guardas (último owner não sai/rebaixa; último membro não abandona equipe c/ projetos), transferência de projeto pessoal → equipe (libera cota free), export LGPD c/ `teamMemberships`, painel Equipes no web c/ aceite automático pós-login. **19 testes por papel = gate M2.** Smoke real no Chrome (Ana cria → link → Beto entra). Por quê assim: e-mail real não existe ainda → link copiável; enumeração de e-mail era requisito C9 da revisão v2; RBAC fino na app (não na RLS) era decisão do plano v2.
7. **Landing como página inicial** (2 iterações no mesmo dia, pedido do Pedro): v1 = onboarding de 4 cartões na 1ª visita; v2 (final) = **página inicial de verdade** — todo acesso à raiz cai nela, intro + aviso legal do README logo após a descrição, botão Entrar/conta no canto superior direito (posição do avatar), **CTA único "Editor / Validador de Gaiola"** c/ ícone (importar/assistente/exemplo moram dentro do editor), fundo grid técnico + animação escalonada (respeita `prefers-reduced-motion`). Por quê: a 1ª tela jogava o visitante direto num editor denso (fricção A1 do estudo); Pedro preferiu 1 CTA a 3 cartões p/ não forçar escolha prematura. Junto: **topbar compacta** (disclaimer 1 linha + "Sobre o portal" reabre a landing — R5 parcial) e **fix do z-index** (drei `Html` c/ `zIndexRange=[40,0]`, overlay c/ z-index 200, landing 300). Artefato do estudo atualizado (seção 3 c/ fluxo implementado, A1 resolvida, R1 no ar).
8. **Decisão registrada — login com Google:** entra na fase 12 (Cognito real) como IdP federado do user pool; sem mudança na API (claims iguais, bootstrap idempotente). Ponto em aberto: linking de contas (mesmo e-mail via Google × cadastro direto gera subs diferentes — decidir entre Lambda `PreSignUp` c/ `AdminLinkProviderForUser` ou aceitar contas separadas).

**Incidente aprendido:** branch de telas criada a partir da main (sem o PR #9) c/ worktree sujo → `add -A` commitou `apps/api/.dev/pgdata` (1320 arquivos) e a troca de branch corrompeu o banco dev. Corrigido (branch recriada limpa, force-push, DB recriado). **Regras: branch dependente nasce do branch da dependência; `git status --short` antes de `add -A`; `.dev/` está no .gitignore.**
